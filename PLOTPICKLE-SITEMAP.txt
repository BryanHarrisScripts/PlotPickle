PLOTPICKLE DEFINITIVE SITEMAP
=============================

Purpose
-------

This file is the architectural sitemap and ownership map for PlotPickle.

It answers four questions:

1. Where does a Human go to do something?
2. Which PlotPickle subsystem owns that capability?
3. Which screens may link to it without duplicating it?
4. How do STORY, Wyrmwood, BUZZ, PPF, Agents and the authoring workspaces remain one operating system rather than disconnected plugins?

The governing rule is:

EVERY CAPABILITY HAS ONE CANONICAL HOME.

A capability may be linked or launched from several places, but it should not gain a second source of truth, second editor, second authority model, second agent runtime, second canon store or second project representation merely because another experience needs it.

STORY: The Unwritten is therefore a first-class PlotPickle experience, not a loose game plugin. It consumes and contributes to PlotPickle projects through the same PPF, Plan, Build, Library, Agent, Context, canon and authority systems used by the rest of PlotPickle.

Status vocabulary
-----------------

CURRENT  = present in the current product architecture or shipped surface.
TARGET   = approved architectural destination that may still require implementation.
LATER    = intentionally deferred extension.

STORY COUPLING CONTRACT
=======================

The most important STORY navigation and architecture rule is:

A STORY GAME STARTS FROM PLOTPICKLE STORY DATA WHEN THAT DATA ALREADY EXISTS.

A Human who has already built a story in PlotPickle must not be asked to recreate the story in a separate STORY setup wizard.

Example:

Library
  -> My Stories
    -> "My Existing Story"
      -> Play in STORY
        -> PlotPickle loads that project's PPF
        -> STORY derives the legal playable starting state
        -> Human selects game/session scope
        -> STORY validates it
        -> STORY Game Table

The same launch should also be available from the current project on Dashboard and from STORY Home.

If the project lacks information STORY needs, STORY must reuse the canonical PlotPickle owner of that information.

Example:

STORY needs a central conflict
  -> existing project has none
    -> open or embed Plan / Foundations / Conflict
      -> save through normal PlotPickle project authority
        -> return to STORY preflight

Do NOT create:

STORY Conflict
STORY Character
STORY Location
STORY Theme
STORY World
STORY Canon

as parallel versions of existing PlotPickle concepts.

Instead:

PlotPickle Concept        -> used by STORY
PlotPickle Premise        -> used by STORY
PlotPickle Character      -> represented as a Story Piece when playable
PlotPickle Location       -> represented as a Story Piece / scene location when playable
PlotPickle Relationship   -> projected into STORY state
PlotPickle Object         -> represented as a Story Piece when relevant
PlotPickle Secret         -> projected through STORY knowledge boundaries
PlotPickle Conflict       -> projected into active STORY pressure/objectives
PlotPickle World Rule     -> enforced by STORY where modeled mechanically
PlotPickle Structure      -> available to seed scene/session scope
PlotPickle Canon / PPF    -> durable authority
STORY Session State       -> temporary authoritative game/session state
Approved STORY Outcome    -> may be admitted back through the existing PPF authority path

This is how STORY remains coupled to the PlotPickle operating system while still being a distinct playable experience.


STARTING A NEW STORY THROUGH STORY
==================================

A Human may also begin from STORY with no existing project.

That path must still create a normal PlotPickle project and use the same PlotPickle concepts/questions already owned by Plan / Foundations.

STORY Home
  -> Start New Story
    -> Create normal PlotPickle project
    -> Minimal PlotPickle Foundations
      -> What is your story about?       -> Concept
      -> Who is it about?                -> Character
      -> What do they want?              -> Desire / Goal
      -> What stands in their way?       -> Conflict
      -> Where does it happen?           -> World / Location
      -> What kind of story is it?       -> Genre / Tone / Style
    -> Save through normal project / PPF path
    -> Derive minimum playable STORY state
    -> Validate
    -> Play

The questions may be presented with a playful STORY visual treatment, but the fields, persistence and ownership remain PlotPickle's.

This prevents STORY from becoming a loose plugin and means anything created while preparing to play can immediately be used by Plan, Build, Write, Storyboard, Previs, Reports and the rest of PlotPickle.


PLAYING AN EXISTING PLOTPICKLE STORY
====================================

The existing-story path is a core requirement, not a later convenience.

Minimum behavior:

1. Human opens STORY Home, Dashboard or Library.
2. Human chooses an existing PlotPickle story/project.
3. PlotPickle loads the project's approved PPF data.
4. STORY derives only the scene/session-relevant working set.
5. STORY identifies any missing minimum playable information.
6. Missing information is completed through the canonical PlotPickle Plan/Build owner.
7. STORY performs deterministic preflight / validation.
8. Human chooses a starting scope or mode.
9. STORY creates a session linked to the source project.
10. Play occurs through STORY's deterministic session state machine.
11. STORY records actions, consequences, provenance and checkpoints.
12. Session results do not silently rewrite durable PPF canon.
13. Human may review selected outcomes and explicitly admit approved changes to the project.
14. The same project can then continue through Plan, Build, Write, Storyboard, Previs, Edit, Reports or another STORY session.

This creates a closed PlotPickle loop:

Learn
  -> Plan
    -> Build
      -> STORY
        -> Consequence
          -> Reflect
            -> Approve durable changes
              -> PPF
                -> Write / Storyboard / Previs / Refine / Reports
                  -> STORY again

STORY is therefore both a destination and an alternate way to interact with an existing PlotPickle storyworld.


CANONICAL OWNERSHIP RULES
=========================

1. Library owns project discovery and selection.
2. Plan owns story foundations and world definition.
3. Build owns structural arrangement.
4. STORY owns playable session state, legal actions, deterministic game resolution and session consequences.
5. PPF owns durable project/canon authority.
6. Agents own execution identities and remain bounded by PlotPickle trust.
7. Context Engine owns transient, minimal context assembly.
8. BUZZ owns social discovery, presence, rooms and invitations.
9. Wyrmwood owns its teaching-game product experience.
10. LEARN owns curriculum.
11. Storyboard owns visual board/frame planning.
12. Previs owns timed production visualization.
13. Write owns screenplay/treatment writing.
14. Edit owns editorial review.
15. Feedback owns review notes/proposals/approvals.
16. Refine owns specialist craft diagnostics/refinement.
17. Reports owns evidence/reporting views.
18. Settings owns configuration, not story content.

A new feature should be rejected or redirected if it creates a second owner for an existing concept without an explicit architecture decision.


NAVIGATION RULES
================

A screen may appear in more than one launch path without becoming more than one capability.

Examples:

Library -> Story -> Play in STORY
Dashboard -> Current Project -> Play in STORY
STORY Home -> Play Existing Story -> Library selector
BUZZ -> World -> Join STORY
Wyrmwood -> Begin Trial -> STORY-compatible runtime

These are launch aliases.

They must converge on the same underlying owner and project/session contracts.


DEPTH CHECK
===========

The deepest meaningful information hierarchy remains the story itself, not Settings.

PlotPickle
  -> Project
    -> Build
      -> Story Structure
        -> Act
          -> Sequence
            -> Block
              -> Scene
                -> Mini-Block
                  -> Beat
                    -> Storyboard
                      -> Frame / Shot
                        -> Visual continuity / generation material

STORY adds another traversal of the same storyworld rather than another copy of it:

PlotPickle
  -> Project / PPF
    -> STORY
      -> Session
        -> Scene
          -> Active Working Set
            -> Character / Location / Object / Conflict / Secret
              -> Legal Action
                -> Deterministic Resolution
                  -> Consequence
                    -> Review / Canon Admission


ARCHITECTURAL SANITY TEST
=========================

Before adding a new screen, route, agent, editor, game mechanic or data store, ask:

1. What existing PlotPickle concept does this use?
2. Who already owns that concept?
3. Can this new experience project or link to the existing owner instead of duplicating it?
4. What is the authoritative state?
5. Is temporary state clearly separated from durable PPF canon?
6. Is AI proposing/interpreting while deterministic code owns mechanical authority where required?
7. Does this create a second agent runtime, knowledge graph, canon store, project model or editor?
8. Can the Human move between STORY and the rest of PlotPickle without re-entering data?
9. Can a project created here immediately continue through the rest of PlotPickle?
10. Does the feature have exactly one canonical home in this sitemap?

If the answer to #7 is yes without a deliberate architecture decision, the design is probably wrong.


END STATE
=========

PlotPickle is one operating system for story creation, learning, play, visualization, production and collaboration.

LEARN teaches the grammar.
PLAN defines the story.
BUILD structures it.
STORY lets Humans and bounded agents inhabit and change a playable session derived from it.
PPF decides what becomes durable truth.
STORYBOARD and PREVIS visualize it.
WRITE and EDIT express it.
REFINE and REPORTS evaluate it.
BUZZ connects people around it.
WYRMWOOD teaches through play.

FORGIVING SHELL MIGRATION MAP
==============================

Status: Phase 2B / issue #1722, 2026-09-06.

This section records how the definitive architecture above is presented through the forgiving shell. It is presentation and verification metadata, not a second capability map or route registry.

Governing presentation rules
----------------------------

1. The authenticated creative shell exposes no more than six normal top-level areas: Home, Create, Produce, Review, Connect / Play and Settings.
2. GLOBAL_SHORTCUTS remains the runtime source of truth for canonical global destinations and keyboard shortcuts.
3. A contextual child may appear in the shell without becoming another global shortcut.
4. Public / Startup / First Run / DEMO / profile-access surfaces remain outside the authenticated creative shell where that boundary protects onboarding, disposable DEMO state or Human-private identity.
5. STORY keeps its existing self-owned single PlotPickleWorkspaceShell. The release boundary must never wrap /story a second time.
6. Agents, Skills, PPF, Context / Story Graph and AI Runtime are capability subsystems or authority layers. Sitemap depth does not promote them into additional top-level navigation areas.
7. A launch alias may preserve an old or convenient URL/shortcut while the shell reports the capability's truthful owner and context.
8. Nested sitemap rows inherit their canonical owner's migration class unless they have a separately addressable route recorded below.

Ownership clarifications found during migration
-----------------------------------------------

PageFlow
  PageFlow is a Refine diagnostic over Write-owned screenplay evidence. The existing W shortcut continues to launch /pageflow as a compatibility/convenience alias because #1719 preserved keyboard behavior. The page does not gain ownership of screenplay text, and the shell identifies the PageFlow diagnostic context rather than creating a second Write or Refine owner.

Voiceprint
  Current code identifies Voiceprint definitions as Plan-owned character voice definitions. Refine may compare screenplay text against those definitions, but Voiceprint itself remains a Plan contextual child.

Labs
  /labs is intentionally contextual. scope=plan maps to Create, scope=storyboard maps to Produce, and scope=feedback or scope=refine maps to Review. Labs does not become a seventh top-level area.

Collab and BUZZ
  Community / BUZZ remains the social owner for rooms, presence, public conversations and discovery. Formal Collab remains a distinct collaboration capability. During #1722, /?workspace=collab is restored as an authority-safe contextual entry that routes discussion to Community, review decisions to Feedback, revisions/proposals to Native Git and provider setup to Settings without mounting the retired rich-project localStorage model. Issue #1723 owns restoration of the full formal Collab UI on the current profile-owned PPF authority. /buzz remains a compatibility launch alias and does not gain project or STORY ownership.

Subsystems
  Agents, Skills, PPF, Context / Story Graph and AI Runtime keep their existing architectural ownership. They are reached through the workspaces and Settings surfaces that need them; they are not promoted simply because they have deep sitemap trees.

Audit reconciliation
--------------------

The UI Continuity registry audits actual current routes rather than legacy workspace aliases. Retired audit aliases such as ?workspace=storyboard, ?workspace=write, ?workspace=pitch, ?workspace=feedback, ?workspace=refine and ?workspace=reports are not treated as canonical routes.

The read-only UI Continuity Agent verifies:
- no more than six normal areas;
- full canonical global-destination reachability;
- deterministic area membership;
- current area and destination;
- contextual child identity where applicable;
- persistent project/save/status truth;
- intentional Public / Startup exceptions;
- return paths, focus/anchor protections and navigation overlap.

Rendered CI keeps browser work bounded while covering one authenticated representative of every area plus STORY. Deterministic registry/source tests cover the complete migration ledger.

Migration completion rule
-------------------------

A CURRENT or TARGET sitemap capability is considered migrated when its canonical owner is classified above and every separately addressable user-facing route is either:

1. a canonical shared-shell destination;
2. a contextual child in the correct forgiving area; or
3. an explicit Public / Startup exception.

This classification never changes the underlying authority merely to simplify navigation. The defining rule remains:

EVERY CAPABILITY HAS ONE CANONICAL HOME.
