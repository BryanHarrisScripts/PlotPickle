# #3142 — One-shot owner-authorized coding worker: bounded source edit

October 25, 2026. This is the first executable source-mutation slice toward the independent engineering dispatcher. It is deliberately separate from the existing read-only supervisor and the one-shot OBSERVE gateway.

## Delegation and authority

The local Windows operator must provision a private, single-use `engineering-edit-once` grant in `%LOCALAPPDATA%/PlotPickle/engineering-team/conversation-gateway/owner-coding-grants/<grantId>.json`. Its exact fields are validated by `validateCodingGrant`: a 32-character random grant ID; issue number; exact clean MAIN commit; one `scripts/engineering-team/**/*.mjs` file and its SHA-256 content digest; one `tests/issue-*.test.mjs` focused-test identity; a bounded owner-specified objective; model identifier; output-token cap; expiration within one hour; `maxRequests: 1`; and exact consent `AUTHORIZE_ONE_ENGINEERING_SOURCE_EDIT`. This narrow local grant is **not** created by a remote issue, browser, ChatGPT tool, AI response, or this worker. Credentials come only from the local `OPENAI_API_KEY` environment and never enter GitHub.

The only native entry point is `node scripts/engineering-team/gateway/authorized-coding-once.mjs --once <grantId>`, run from the owner Windows checkout. Clean MAIN and trusted Git origin are established through the existing `gatewayAppSource`. This CLI is **not** mounted as a remotely invocable MCP tool or attached to the observer supervisor. Importing the module has no side effects.

## Bounded edit and durable result

The worker checks one target file, its digest, and a named existing focused test before reserving the grant in a private write-once receipt. It then creates an isolated detached Git worktree at the exact source commit and a grant-specific local branch, makes **one** Responses API request with `store:false` and no tools, accepts at most one unique exact text replacement in the granted file, performs only non-executing syntax/diff checks, and commits the edit locally with Git hooks disabled. Model-authored text cannot choose a command, path, test, branch, merge, network destination, or credential.

Generated code is **not run on the owner's Windows host**. The focused-test identity travels with the receipt but execution belongs to a subsequent independent, isolated CI verifier. A successful worker returns `LOCAL_COMMIT_PREPARED`, not “issue fixed”: the result contains the branch, exact commit, focused-test path, and explicit `focusedTestExecuted:false`, `pullRequestCreated:false`, `independentVerification:false` and `automaticMergeAuthorized:false`.

A write-once stage sentinel and a serialized private admission lock allow one new coding stage at a time, subject to a native disk-capacity probe requiring at least 9 GiB available before a grant is consumed. Retained stages, including uncertain or crashed attempts, are preserved as evidence and do not consume an arbitrary three-stage quota; unknown entries, inventory overflow, failed disk probes or an orphaned lock fail closed and require owner inspection rather than age-based deletion. A reservation is fsynced before external requests or source mutation; duplicate delivery cannot replay it. If a model request, edit, Git command, receipt or local operation becomes uncertain, the stage stays for inspection and the worker fails closed. No worktree is automatically deleted, no blocked Factory reservation is replayed, no Pi dispatcher is started and no existing task or app is restarted.


## Draft PR publication slice (not yet unattended)

The inert `publication/authorized-pr-publish-once.mjs` Windows CLI accepts `--once <publicationId>` only. It requires a **second**, locally provisioned owner grant in `owner-publication-grants/<publicationId>.json`; the coding grant alone cannot authorize GitHub writes. Exact v1 fields: `schemaVersion:1`, `kind:"draft-pr-publish-once"`, distinct 32-hex `publicationId` and coding `grantId`, `issueNumber`, clean MAIN `sourceHead`, `localCommit`, deterministic `branch` (`engineering/<issue>-<grantId>`), `targetPath`, expiry within one hour, `maxRequests:1`, and `consent:"AUTHORIZE_ONE_DRAFT_ENGINEERING_PR"`. A scoped `PLOTPICKLE_GITHUB_PUBLISH_TOKEN` is supplied only through the owner's local environment; it must have the minimum repository Git contents and pull-request write permissions. Never put tokens in GitHub, issues, prompts or receipts.

Publication verifies the original edit grant, exact prepared result, clean isolated staged Git worktree, one changed path, exact source parent, local tree and blob. It uses fixed GitHub Git-data REST endpoints, not shell-driven `git push`: verify remote MAIN; upload the committed source blob and verify its Git SHA; build and verify the exact Git tree; create a remote commit with the approved parent/tree; create a new deterministic branch ref; recheck MAIN; then create a **draft** PR with a fixed, non-model-authored title/body and explicit pending CI/Windows verification. The remote commit SHA may differ from the local commit SHA; the durable result records both identities and the verified identical tree. No force-update, arbitrary shell, merge, test execution or implicit queue admission is allowed.

The first external request is preceded by a write-once private reservation. Every uncertain response remains permanently non-replayable; later recovery may only reconcile read-only evidence before a separately authorized new attempt. Fixture tests exercise wrong local parent/path, missing token, remote MAIN drift, exact tree/blob mapping, draft PR metadata, duplicate delivery and uncertain branch publication. These fixtures are not proof of live GitHub publication or owner-host Windows acceptance. The Software Factory startup path does **not** currently launch the coding worker or publisher. Revocable supervisor startup, STOP/Pause, independent CI/Windows verifier receipts and a genuine owner-granted publication cycle remain separate acceptance steps.

## #3142 — separately authorized draft-PR publication

The first publishing slice lives in `scripts/engineering-team/gateway/publication/authorized-pr-publish-once.mjs`. It consumes a **different** private, write-once `draft-pr-publish-once` grant stored in `%LOCALAPPDATA%/PlotPickle/engineering-team/conversation-gateway/owner-publication-grants/<publicationId>.json`. The grant binds `publicationId`, coding `grantId`, issue number, original clean MAIN source SHA, exact prepared local commit, one canonical `engineering/<issue>-<grantId>` branch, approved source path, expiry within an hour, `maxRequests:1` and `AUTHORIZE_ONE_DRAFT_ENGINEERING_PR`. It must match both the private coding grant and the `LOCAL_COMMIT_PREPARED` coding receipt. A successful code edit grants **no** implicit publishing permission.

The publisher reads the source from the *committed Git blob* in the existing isolated worktree, verifies exact parent, local branch, single changed path, clean worktree and local tree, and checks the current remote MAIN SHA. It never runs generated code on the owner's computer. Using a separately owner-provisioned `PLOTPICKLE_GITHUB_PUBLISH_TOKEN` from the local environment, it calls only fixed GitHub Git-data endpoints to create a matching blob, tree, commit, and new branch, followed by the GitHub endpoint to open a **draft** PR against `main`. The returned GitHub blob SHA and tree SHA must equal the local commit's Git objects. The remote commit identity may differ because GitHub records different commit metadata; both exact SHAs and the identical tree are retained in the receipt. No `git push`, arbitrary shell, force update, existing branch overwrite, PR-ready transition, merge, or automatic acceptance is permitted.

The publisher creates an fsynced, write-once private reservation **before the first remote request**. Any timeout, mismatched API response, stale MAIN, ambiguous external side effect, or failed local receipt remains `PUBLISH_STARTED_UNCONFIRMED`; it is **not retried** blindly, cleaned up, or reported as a published PR. The owner can reconcile uncertainty using GitHub's observed branch/PR state and durable local receipts; automatic reconciliation and resumed dispatch are separate milestones. A verified creation returns `DRAFT_PR_CREATED`, the PR number/URL, source SHA, local and remote commits, tree, and `independentVerification:false`.

Two native Windows-compatible local commands are provided:
- `node scripts/engineering-team/gateway/publication/authorized-pr-publish-once.mjs --once <publicationId>` — publish an already prepared coding commit.
- `node scripts/engineering-team/gateway/authorized-coding-once.mjs --once-and-publish <codingGrantId> <publicationId>` — execute the approved code edit and automatically hand its completed receipt to the separately authorized draft publisher, with no interactive handoff between the two stages. If either grant or any proof is missing, the sequence stops.

Unit/fixture tests use a **real disposable Git repository and worktree**, with a deterministic fake GitHub HTTPS endpoint. They check the exact Git tree and draft-PR body, lack of merging, remote SHA mismatch, stale MAIN, lost creation response/no-replay, invalid grants, dirty stage and one-call handoff. These tests do **not** prove the owner's token or real GitHub publication, owner-machine startup/reboot, unattended queue, independently executed generated code, live model completion or Product Gate. The runner selects native Windows testing for both coding and publishing source changes, and the approved W8/W9 truth binding pins the revised inputs. Both PR Gate and owner-host Product Gate are still required on the exact candidate head.

Next: authenticate and store owner-scoped grants without Human per-issue babysitting, add read-only recovery reconciliation for ambiguous PR publication, then connect to the Windows-owned supervisor and persistent dispatcher lease/STOP path. ## #3302 — two independently evidenced replies (first bounded implementation)

A single owner-issued coding grant and a **different** owner-issued draft-PR publication grant now lead to two **separate durable receipt families** under `scripts/engineering-team/gateway/verification/two-receipt-verifier.mjs`. This is the first closed-form verifier, not a claim of a complete always-on dispatcher.

**Engineering reply:** after a successfully published draft PR, the local `--once-and-publish` operation automatically issues a write-once `engineering-receipts/<codingGrantId>.json`. It cross-checks the private owner coding grant, prepared local commit receipt, separate publication grant, pre-network publication reservation and confirmed GitHub publication result. The output includes request/receipt IDs, exact MAIN ancestor, local commit, published remote HEAD, Git tree and content digest, one changed source file, focused-test identity and PR number. The code change is real in the publisher's exact-tree boundary, but `focusedTestExecuted:false` and `independentlyVerified:false` remain explicit. If the engineering receipt cannot be issued, publication cannot be replayed and the combined CLI returns `DRAFT_PR_RECEIPT_UNVERIFIED`.

**Independent verifier reply:** `--verify <codingGrantId> <newVerificationAttemptId>` runs a separate read-only evidence collector with its **own** write-once reservation and result under `verification-receipts/`. It uses a dedicated local `PLOTPICKLE_GITHUB_VERIFY_TOKEN` for fixed GitHub GET routes, independently rereads the draft PR and exact remote commit parent/tree, the newest Architecture Verification workflow run for that SHA, seven individually green architecture jobs and the selected hosted-Windows coding-worker step. Missing, skipped, cancelled, timed-out, stale or failed requirements yield `WAITING` or `BLOCKED`; previous green runs cannot substitute for a newer failing run.

**Owner Windows acceptance is separate from hosted CI.** The verifier may report `INDEPENDENTLY_VERIFIED` only when an independently provisioned Ed25519 public key verifies a canonical, exact-request-and-SHA-bound owner-Windows witness. The owner verifier's **private signing key must not be stored or usable in the coding worker/publisher process**. A test-generated Ed25519 witness proves the signature boundary, not real owner-host acceptance. There is no production owner verifier signer or supervisor/queue integration in this PR, so the live path correctly stays `OWNER_WINDOWS_EVIDENCE_MISSING_OR_INVALID` until that independent infrastructure exists.

The verifier never mutates GitHub, starts or stops the Factory, runs the model, executes generated code, repairs staging, replays uncertain requests, or merges. Every verifier attempt is independently keyed and immutable. A read-only recheck needs a new ID; prior failed evidence remains intact. Neither engineering nor verifier receipt sets `automaticMergeAuthorized:true`. The next increments are a restricted signed owner verifier, a revocable Windows supervisor poll/lease, independent product/UAT proof, and exact-head green-only merge policy. Until a **real** issue-to-PR-to-verified-owner-Windows cycle is observed, #3302 and #3142 remain open and PR #3311 remains draft.
